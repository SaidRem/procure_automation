## ADR-001 — Product / ProductInfo separation

Date: 2026-08-28

Status: Accepted

Decision:

Логический товар (`Product`) и предложение товара конкретным поставщиком
(`ProductInfo`) — отдельные сущности. `Product` хранит независимые от
поставщика данные (название, категория). `ProductInfo` хранит цену,
рекомендуемую розничную цену, остаток и модель для конкретной пары
(`Product`, `Shop`).

Reason:

- Один товар продаётся несколькими поставщиками по разным ценам.
- Импорт прайса одного поставщика не должен затрагивать данные других
  поставщиков или сам логический товар.
- Требование бизнес-правил: изменение каталога не должно изменять
  историю уже оформленных заказов (обеспечивается отдельно, см. ADR-003).

Consequences:

- `catalog.Product` и `catalog.ProductInfo` — разные модели с
  `unique(product, shop, external_id)` на `ProductInfo`.
- Импорт прайса поставщика затрагивает только `ProductInfo` (и связанные
  `ProductParameter`) этого `Shop`, не трогая `Product` других
  поставщиков.
- Каталожная выдача (список товаров) строится через `ProductInfo` с
  `select_related`/`prefetch_related` на `Product`, `Shop`, параметры.

## ADR-002 — Suppliers as a separate Django application

Date: 2026-08-28

Status: Accepted

Decision:

Функциональность поставщика (модель `Shop`, включение/отключение приёма
заказов, импорт и экспорт прайса) выносится в отдельное приложение
`suppliers`, а не объединяется с `catalog`.

Reason:

- Первоначальный архитектурный план закладывал отдельные домены
  `catalog` и `suppliers`; решение подтверждает этот выбор после
  анализа требований.
- `Shop` — самостоятельная бизнес-сущность с собственным жизненным
  циклом (регистрация как пользователь типа `shop`, включение/выключение
  приёма заказов), не сводящаяся к части каталога.
- Разделение позволяет независимо развивать логику поставщиков
  (в будущем — договоры, верификация, KPI) без разрастания `catalog`.

Consequences:

- `catalog.ProductInfo` и `catalog.Category` ссылаются на
  `suppliers.Shop` через FK/M2M — зависимость на уровне моделей (ORM)
  `catalog → suppliers`, однонаправленная.
- Обратный прямой импорт ORM-моделей (`suppliers` импортирует модели
  `catalog` напрямую) не допускается.
- Обращение `suppliers` к данным `catalog` (например, сервисы импорта
  прайса, инициируемые в `suppliers`) допускается только через
  публичный сервисный слой `catalog.services`. Это не является
  запрещённой ORM-зависимостью: `suppliers` не импортирует и не
  обращается к моделям `catalog` напрямую, а использует только его
  публичный интерфейс.
- Django-приложения проекта: `users`, `suppliers`, `catalog`, `orders`,
  `notifications`.

## ADR-003 — OrderItem snapshot strategy

Date: 2026-08-28

Status: Accepted

Decision:

`OrderItem` хранит snapshot-поля состояния товара на момент подтверждения
заказа (наименование товара, магазин, цена, рекомендуемая розничная
цена) в дополнение к FK на `ProductInfo`. FK на `ProductInfo` делается
nullable с `on_delete=SET_NULL`.

Reason:

- Импорт прайса не должен нарушать историчность заказов.
  Конкретная стратегия обновления ProductInfo (обновление существующих
  записей или пересоздание) определяется при реализации сервиса импорта.
- Без snapshot-полей историчность нарушается при любой стратегии: при
  пересоздании записей заказ теряет данные о цене и наименовании, при
  обновлении на месте — начинает отражать текущую цену вместо цены на
  момент заказа.
- Бизнес-правило: данные, участвующие в финансовых операциях, должны
  сохранять состояние на момент операции.

Consequences:

- Сумма и содержимое исторических заказов вычисляются по snapshot-полям
  `OrderItem`, а не по текущему состоянию `ProductInfo`.
- FK `OrderItem.product_info` становится необязательным и служит только
  для дополнительной трассируемости (переход к актуальной карточке
  товара), не для расчётов.
- Snapshot-поля заполняются один раз в сервисе подтверждения заказа
  (`orders/services`) и далее не изменяются.

Related decisions:

- ADR-008 — Supplier import strategy. Фиксирует стратегию обновления
  `ProductInfo` при импорте (upsert, soft-deactivation), которая на
  момент принятия ADR-003 была оставлена открытой.
- ADR-009 — Shopping cart model. Определяет, что до подтверждения заказа
  `OrderItem` находится в состоянии корзины и snapshot-поля ещё не
  заполнены.
- Историчность адреса доставки — открытый вопрос, решается по этой же
  стратегии при проектировании `orders`. `users.Contact` намеренно
  оставлен без soft delete (step 1): удаление адреса не должно изменять
  историю уже оформленных заказов, поэтому `Order` будет хранить
  snapshot адреса на момент подтверждения, а не полагаться на FK к
  `Contact`. Конкретные поля и правило `on_delete` фиксируются отдельным
  ADR при реализации приложения `orders`.

## ADR-004 — Custom User model

Date: 2026-08-28

Status: Accepted

Decision:

Используется кастомная модель `User` (наследник `AbstractUser`) с email в
качестве `USERNAME_FIELD`, полем `type` (`buyer` / `shop`) и
`is_active=False` по умолчанию до подтверждения email.

Reason:

- Спецификация API проекта требует авторизацию и регистрацию по
  email/паролю, без отдельного username в бизнес-сценарии.
- Роли пользователя (клиент и поставщик) должны различаться на уровне
  модели для разграничения прав доступа (кто может импортировать прайс,
  кто оформляет заказы).
- Подтверждение регистрации по email — часть базовых требований проекта.

Consequences:

- `AUTH_USER_MODEL` должен быть установлен в `settings.py` на модель
  `users.User` до первой миграции проекта (важно: изменение
  `AUTH_USER_MODEL` после миграций требует пересоздания БД).
- На текущем этапе роли buyer/shop реализуются через поле type.
  При расширении системы рекомендуется рассмотреть Django Groups/Permissions
  для более гибкой модели доступа.
- `suppliers.Shop` связывается с `users.User` через `OneToOneField`.

## ADR-005 — Celery architecture

Date: 2026-08-28

Status: Accepted

Decision:

Celery с брокером Redis используется для трёх типов фоновых задач:
`send_email` (домен `notifications`), `do_import` и `do_export` (домен
`suppliers`, работают через публичные сервисы `catalog.services` для
записи/чтения каталога).

Reason:

- Продвинутая часть требований проекта прямо требует вынести медленные
  операции (email, импорт, экспорт) в Celery-задачи.
- Импорт/экспорт прайса и отправка email — I/O-bound операции
  (HTTP-запрос за YAML, отправка почты), блокирующие обработку запроса
  при синхронном выполнении.

Consequences:

- `notifications` владеет задачей `send_email` и публичным сервисным
  слоем `notifications.services`. Другие домены (`users` —
  подтверждение регистрации и сброс пароля, `orders` — подтверждение
  заказа, накладная администратору, смена статуса, `suppliers` —
  уведомления поставщику) вызывают только функции
  `notifications.services` и не импортируют Celery-задачи напрямую.
  Цепочка вызова: `<app>.services` → `notifications.services` →
  Celery task.
- В Celery-задачи передаются только сериализуемые примитивы
  (идентификаторы объектов), не инстансы моделей.
- Постановка задачи в очередь выполняется через
  `transaction.on_commit()` внутри `notifications.services`, чтобы
  воркер не начал обработку до коммита транзакции.
- `suppliers` владеет задачами `do_import`/`do_export`; для изменения
  данных каталога использует только публичные функции
  `catalog.services`, не ORM `catalog` напрямую — такое обращение
  разрешено правилом ADR-002 (запрещён только прямой импорт ORM-моделей
  в обратном направлении, обращение через сервисный слой допускается).
- Вью админки склада запускает `do_import` асинхронно и не ждёт
  результата синхронно.
- Требуется добавить `CELERY_*`-настройки и конфигурацию Celery-app в
  `config/` (отсутствуют на момент принятия решения).

## ADR-006 — Service layer architecture

Date: 2026-08-29

Status: Accepted

Decision:

Бизнес-операции реализуются через сервисный слой приложений.

Views, serializers и Celery tasks не содержат бизнес-правила.

Reason:

- уменьшение связности;
- тестируемость;
- разделение ответственности.

Consequences:

Пример:

views.py
    |
    v
services/order_service.py
    |
    v
models.py

## ADR-007 — API authentication strategy

Date: 2026-08-29

Status: Accepted

Decision:

Аутентификация API строится на JWT.

Реализация — библиотека `djangorestframework-simplejwt`.

Reason:

- Требуется stateless-аутентификация для REST API, используемого
  как внешними клиентами, так и фронтенд-приложением.
- `djangorestframework-simplejwt` — стандартное для DRF решение,
  совместимое с кастомной моделью `User` (ADR-004, email как
  `USERNAME_FIELD`).

Consequences:

- Детали реализации (время жизни токенов, refresh/rotation,
  blacklist, набор endpoints выдачи и обновления токена, настройки
  `SIMPLE_JWT` и `REST_FRAMEWORK`) на данном этапе не фиксируются
  и определяются при реализации.

Implementation notes (step 1):

- Зафиксированы времена жизни токенов: access — 60 минут, refresh —
  1 сутки (`SIMPLE_JWT` в `config/settings.py`).
- Rotation (`ROTATE_REFRESH_TOKENS`) и blacklist
  (`BLACKLIST_AFTER_ROTATION`) на текущем этапе отключены: blacklist
  требует приложения `rest_framework_simplejwt.token_blacklist` с
  собственными миграциями и хранением состояния токенов в БД, что
  избыточно для инфраструктурного этапа.
- Rotation и blacklist могут быть включены позже — например, при
  появлении требований к принудительному завершению сессий или отзыву
  refresh-токенов. Это изменение настроек и добавление приложения
  `token_blacklist`, оно не затрагивает принятое решение
  (JWT + `djangorestframework-simplejwt`) и не требует нового ADR.

## ADR-008 — Supplier import strategy

Date: 2026-08-29

Status: Accepted

Decision:

Импорт прайса поставщика выполняется стратегией upsert по ключу
`(shop, external_id)`, а не полной заменой (delete + recreate).

- Существующие `ProductInfo` обновляются на месте, `id` записи
  сохраняется.
- Отсутствующие в новом прайсе `ProductInfo` этого `Shop` не удаляются,
  им проставляется `is_active=False` (soft-deactivation).
- При возврате товара в прайс существующая запись реактивируется
  (`is_active=True`), новая не создаётся.
- `quantity=0` не означает деактивацию: ноль остатка — товар присутствует
  в прайсе, но временно отсутствует на складе; деактивация означает, что
  предложение снято с продажи поставщиком.
- `Product`, `Category` и `Parameter` при импорте не удаляются.

Схема:

- `catalog.ProductInfo.is_active` — `BooleanField(default=True,
  db_index=True)`.
- `catalog.ProductInfo` — `UniqueConstraint(fields=['shop',
  'external_id'])`.

Reason:

- `external_id` — идентификатор предложения на стороне поставщика и
  единственный стабильный ключ между импортами. Название товара,
  категория и цена изменяются, `external_id` — нет.
- Full-replace (`ProductInfo.objects.filter(shop=...).delete()` перед
  пересозданием, как в референсном коде требований) уничтожает `id`
  записей при каждом импорте. С учётом `on_delete=SET_NULL` (ADR-003)
  это обнуляет `OrderItem.product_info` у исторических заказов и у
  активных корзин других пользователей — ссылка на актуальную карточку
  товара, ради которой FK и сохранён, перестаёт работать.
- `do_import` выполняется как Celery-задача с ретраями (ADR-005). Upsert
  идемпотентен; full-replace при повторном запуске задачи создаёт окно,
  в котором каталог поставщика пуст.
- Физическое удаление предложений противоречит правилу проекта:
  исторические данные не удаляются без анализа последствий.

Consequences:

- Каталожная выдача и добавление товара в корзину фильтруют
  `is_active=True`. Деактивированное предложение недоступно для новых
  заказов.
- Импорт выполняется атомарно (`transaction.atomic()`): валидация файла
  прайса предшествует записи, частично обновлённый прайс недопустим.
- История заказов защищена snapshot-полями `OrderItem` (ADR-003) и не
  зависит ни от обновления `ProductInfo` на месте, ни от его
  деактивации.
- Констрейнт `unique(product, shop, external_id)` из ADR-001 заменяется
  на `unique(shop, external_id)`. Прежний констрейнт строго слабее и при
  upsert допускает дубль: если поставщик переносит товар в другую
  категорию или переименовывает его, `product_id` меняется и та же пара
  `(shop, external_id)` проходит проверку повторно.
- Смена `product` у существующего `external_id` трактуется как
  обновление той же записи `ProductInfo`, а не как создание новой.
- Очистка `Product` без активных предложений и отвязка `Category` от
  `Shop` в область этого решения не входят и требуют отдельного ADR.

## ADR-009 — Shopping cart model

Date: 2026-08-29

Status: Accepted

Decision:

Корзина не выделяется в отдельную модель. Корзина — это `orders.Order`
в состоянии `state='basket'`, её позиции — обычные `orders.OrderItem`.

Оформление заказа — переход состояния `basket` → `new`, а не копирование
данных между таблицами.

Reason:

- Структура корзины и заказа идентична: набор позиций с количеством,
  привязка к пользователю, товары от разных поставщиков в одном наборе.
  Отдельные `Basket` / `BasketItem` дублировали бы `Order` / `OrderItem`
  вместе с их сериализаторами и сервисами.
- Подтверждение заказа сводится к смене состояния и фиксации
  snapshot-полей в одной транзакции, без переноса строк между таблицами
  и без риска рассинхронизации корзины и созданного из неё заказа.
- Состояние `basket` присутствует в `STATE_CHOICES` спецификации
  требований — модель состояний заказа изначально описывает корзину как
  одно из них.

Consequences:

- У пользователя не более одной корзины одновременно. Требуется
  частичный уникальный индекс: `UniqueConstraint(fields=['user'],
  condition=Q(state='basket'))`.
- `Order.contact` остаётся nullable: корзина существует без адреса
  доставки. Обязательность контакта проверяется в сервисе подтверждения
  заказа, а не на уровне модели.
- Любая выборка заказов — история клиента, заказы поставщика, админка,
  накладные — обязана исключать `state='basket'`. Это основной риск
  решения: незакрытый фильтр приводит к попаданию чужих корзин в историю
  заказов и в письма. Требуется отдельный queryset/manager
  (`Order.objects.orders()` / `.baskets()`), а не повторение условия в
  каждом месте.
- `Order.dt` (`auto_now_add`) означает момент создания корзины, а не
  оформления заказа. Для истории заказов (спецификация: «Номер, Дата,
  Сумма, Статус») требуется отдельная отметка времени подтверждения;
  конкретное поле определяется при реализации моделей `orders`.

Related decisions:

- ADR-003 — OrderItem snapshot strategy. Пока `Order` находится в
  состоянии `basket`, snapshot-поля `OrderItem` не заполнены: корзина
  обязана показывать актуальные цену и наименование из
  `catalog.ProductInfo`. Snapshot фиксируется один раз при подтверждении
  заказа. Следствие: snapshot-поля `OrderItem` должны допускать пустое
  значение до подтверждения, а расчёт суммы корзины и суммы
  оформленного заказа используют разные источники данных
  (`ProductInfo` и snapshot соответственно).
- ADR-008 — Supplier import strategy. Позиции корзины ссылаются на
  `ProductInfo`, которое может измениться или быть деактивировано между
  добавлением товара в корзину и подтверждением заказа. Выбранная в
  ADR-008 стратегия upsert сохраняет `ProductInfo.id` и поэтому не
  разрушает существующие корзины — сохранность корзин была одним из
  аргументов против full-replace. Сервис подтверждения заказа обязан
  повторно проверить каждую позицию: `ProductInfo.is_active=True`,
  достаточный остаток `quantity`, включённый приём заказов у
  `suppliers.Shop`.

## ADR-010 — Temporary placement of the send_email task

Date: 2026-08-29

Status: Accepted

Decision:

Celery-задача `send_email` временно размещается в приложении `users`
(`users/tasks.py`) и вызывается только через модуль
`users/services/notifications.py`.

ADR-005 не отменяется: целевым владельцем задачи остаётся приложение
`notifications`. Перенос выполняется на шаге 7, когда это приложение
будет создано.

Reason:

- Регистрация и восстановление пароля (шаг 2) требуют асинхронной
  отправки писем, но объём этого шага явно ограничен приложением
  `users`: создание `notifications` в него не входит.
- Альтернатива — синхронная отправка письма из view — противоречит
  ADR-005 и требованиям шага, а также блокирует обработку запроса на
  время SMTP-обмена.
- Отклонение ограничено одним модулем: доменные сервисы `users` уже
  сейчас вызывают не задачу, а функцию-фасад `send_email_async`.
  Цепочка вызова `<app>.services → notifications-фасад → Celery task`
  из ADR-005 сохранена, отличается только местоположение фасада.

Consequences:

- `users/services/registration.py` и `users/services/password_reset.py`
  не импортируют Celery-задачи напрямую — только
  `users.services.notifications.send_email_async`.
- Постановка задачи выполняется через `transaction.on_commit()`
  (требование ADR-005): письмо не уходит, если транзакция регистрации
  откатилась.
- В задачу передаются только примитивы (`subject`, `message`,
  `recipient`), инстансы моделей не сериализуются.
- Перенос на шаге 7 затрагивает два файла (`users/tasks.py` →
  `notifications/tasks.py`, `users/services/notifications.py` →
  вызов `notifications.services`) и не требует изменения доменных
  сервисов и views.
- Пока приложение `notifications` не создано, другие домены не должны
  импортировать `users.tasks`: единственная точка вызова —
  фасад внутри `users.services`.

## ADR-011 — Email confirmation and password reset tokens without database models

Date: 2026-08-29

Status: Accepted

Decision:

Токены подтверждения email и восстановления пароля не хранятся в БД.

- Восстановление пароля использует стандартный
  `django.contrib.auth.tokens.default_token_generator`.
- Подтверждение email использует
  `users.tokens.EmailConfirmationTokenGenerator` — подкласс
  `PasswordResetTokenGenerator`, в хеш-значение которого дополнительно
  входит `user.is_active`.
- Идентификатор пользователя передаётся отдельным полем `uid`
  (`urlsafe_base64_encode`).
- Библиотека `django-rest-passwordreset` не используется.

Reason:

- Одноразовость обеспечивается самим механизмом, без хранения
  состояния: хеш токена сброса включает текущий пароль, поэтому после
  смены пароля токен невалиден; хеш токена подтверждения включает
  `is_active`, поэтому после активации пользователя токен невалиден.
- Отсутствие модели токенов исключает накопление протухших записей и
  необходимость их регулярной очистки.
- Требование проекта — не добавлять `django-rest-passwordreset`;
  реализация опирается на стандартные средства Django.

Consequences:

- В приложении `users` нет новых моделей и миграций: схема БД шага 1
  (ADR-004, docs/database.md) не меняется.
- Срок жизни обоих типов токенов задаётся единственной настройкой
  Django `PASSWORD_RESET_TIMEOUT` (по умолчанию в проекте — 24 часа):
  `check_token` читает её напрямую и не поддерживает отдельный таймаут
  на генератор.
- Известное ограничение: если администратор деактивирует уже
  подтверждённого пользователя, ранее выданный токен подтверждения
  снова становится валидным в пределах `PASSWORD_RESET_TIMEOUT`.
  Риск ограничен возможностью повторной активации самим владельцем
  адреса; при появлении сценария блокировки пользователей потребуется
  отдельное решение (например, отдельный флаг `email_confirmed`).
- Смена email через API профиля не предусмотрена: она потребовала бы
  повторного подтверждения адреса (см. docs/api.md).

## ADR-012 — Shop identity and lifecycle

Date: 2026-08-29

Status: Accepted

Decision:

`suppliers.Shop` идентифицируется связью с пользователем-поставщиком, а
не названием магазина из прайса.

- `Shop.user` — `OneToOneField` на `users.User`, `null=True`,
  `blank=True`, `on_delete=PROTECT`.
- Ключ поиска магазина при импорте — `user`. Название `name` из прайса
  записывается в существующий магазин, а не создаёт новый.
- `Shop.name` — `unique=True`.
- `Shop.url` — `null=True`, `blank=True`: в прайсе поставщика ссылки
  может не быть (`private/shop1.yaml`).
- `Shop.state` (приём заказов) — `BooleanField(default=True)`. Импорт
  прайса значение не изменяет: включение и отключение приёма заказов —
  отдельное действие поставщика.
- Физическое удаление `Shop` не предусмотрено. Прекращение работы
  поставщика выражается через `state=False` и деактивацию его
  предложений (ADR-008).

Reason:

- Референсный код требований (`private/step-3.md`) использует
  `Shop.objects.get_or_create(name=data['shop'], user_id=request.user.id)`.
  При изменении названия в прайсе это создаёт второй `Shop`, а весь
  ранее импортированный каталог остаётся у первого: у поставщика
  появляются два магазина, один из которых виден покупателям с
  устаревшими ценами.
- `name` приходит из внешнего файла и контролируется поставщиком —
  это атрибут, а не идентичность. Пользователь-поставщик
  аутентифицирован сервисом и является устойчивым ключом.
- `PROTECT` на `user` выполняет правило проекта «нельзя физически
  удалять данные без анализа последствий»: удаление пользователя типа
  `shop` вместе с каталогом и историей его заказов должно быть
  осознанным действием, а не побочным эффектом.

Consequences:

- Импорт по URL берёт магазин из `request.user`; импорт из локального
  файла (management-команда) требует явного указания владельца —
  магазин не может быть определён по содержимому файла.
- Пользователя, у которого есть магазин, нельзя удалить, пока магазин
  существует: Django вернёт `ProtectedError`. Это ожидаемое поведение.
- Переименование магазина поставщиком — обновление поля `name`
  существующей записи; `unique(name)` не позволит занять название,
  уже принадлежащее другому поставщику, и такой импорт будет отклонён
  с ошибкой валидации.
- Магазин может существовать без пользователя (`user=NULL`) —
  например, заведённый администратором до регистрации поставщика.
  Импорт для такого магазина возможен только через management-команду.
- Альтернатива `on_delete=SET_NULL` отклонена: магазин без владельца
  продолжает принимать заказы (`state=True`), и отключить его не может
  никто, кроме администратора.

Related decisions:

- ADR-004 — Custom User model. Связь `Shop` с `User` через
  `OneToOneField` зафиксирована там; настоящий ADR определяет правило
  удаления и роль связи как ключа идентификации.

Amendment (2026-08-29, шаг 3.2)

Импорт прайса в каталог не изменяет `Shop`.

- `catalog.services.upsert_shop_price` не записывает поля `Shop`: он
  получает `shop_id`, блокирует строку магазина на время транзакции и
  работает только с данными каталога.
- Поля `Shop.name` и `Shop.url` принадлежат домену `suppliers` и
  обновляются им отдельной операцией. Это уточняет, а не отменяет
  правило выше: название из прайса по-прежнему переносится в
  существующий магазин и нового не создаёт — но делает это `suppliers`,
  а не каталог.
- Следствие для реализации импорта: обновление магазина и запись
  каталога — два разных действия. Если требуется их согласованность,
  внешнюю транзакцию открывает `suppliers` (ADR-016).

## ADR-013 — Category identity strategy

Date: 2026-08-29

Status: Accepted

Decision:

`catalog.Category` имеет собственный первичный ключ. Идентификатор
категории из прайса поставщика первичным ключом не становится и в базе
не хранится.

- `Category.name` — `unique=True`; это ключ поиска при импорте
  (`get_or_create(name=...)`).
- Соответствие «внешний id категории → `Category`» разрешается в
  пределах одного импорта по секции `categories` файла прайса и
  существует только в памяти на время операции.
- Ссылка `goods[].category` на идентификатор, отсутствующий в секции
  `categories` того же файла, — ошибка валидации: импорт отклоняется
  целиком, до записи в базу.
- `Category.shops` (M2M на `suppliers.Shop`) при импорте дополняется
  текущим магазином.

Reason:

- Референсный код (`private/step-3.md`) выполняет
  `Category.objects.get_or_create(id=category['id'], name=category['name'])`,
  то есть подставляет идентификатор из чужой системы в качестве
  первичного ключа. Идентификаторы разных поставщиков независимы:
  `id: 1` в одном прайсе — «Flash-накопители», в другом может быть
  «Ноутбуки». Второй импорт молча переименует чужую категорию или
  привяжет товары к неверной.
- Категория — общая сущность каталога, а не собственность поставщика:
  покупатель фильтрует товары по единому списку категорий, независимо
  от того, сколько поставщиков в ней представлено.

Consequences:

- Категории с одинаковым названием от разных поставщиков — одна запись
  `Category`, связанная с обоими магазинами через `shops`. Это
  требуемое поведение единого каталога.
- Переименование категории поставщиком создаёт новую `Category`;
  прежняя сохраняется вместе со своими товарами и привязками. Слияние
  категорий в область этого решения не входит.
- Внешние идентификаторы категорий не сохраняются, поэтому экспорт
  прайса (шаг 7) не сможет вернуть поставщику исходные `id` категорий
  и будет использовать идентификаторы сервиса. Если появится требование
  сохранять внешние id, потребуется through-модель для `Category.shops`
  и новый ADR.

## ADR-014 — Product identity strategy

Date: 2026-08-29

Status: Accepted

Decision:

`catalog.Product` идентифицируется парой «название + категория».

- `UniqueConstraint(fields=['name', 'category'])`.
- При импорте товар ищется через `get_or_create(name=..., category=...)`.
- `Product` не удаляется при импорте ни при каких условиях (ADR-008).
- Поле `model` (модель товара у поставщика) хранится в
  `ProductInfo`, а не в `Product`, и в идентификации не участвует.
- `Product.category` — `on_delete=PROTECT`.

Reason:

- Один и тот же товар поставляется несколькими поставщиками (ADR-001);
  ключ идентификации не может включать магазин, иначе логический товар
  распадётся на копии по числу поставщиков.
- Название без категории неуникально: «Кабель» в «Аксессуарах» и в
  «Телевизорах» — разные товары.
- `PROTECT` на категории соответствует правилу сохранности данных:
  удаление категории с товарами должно быть осознанным действием.

Consequences:

- Переименование товара поставщиком создаёт новый `Product`.
  Существующее предложение `ProductInfo` при этом не дублируется: по
  ADR-008 запись ищется по `(shop, external_id)`, и смена `product`
  трактуется как обновление той же записи.
- Прежний `Product` остаётся в базе и может не иметь активных
  предложений. Очистка таких записей в область решения не входит
  (ADR-008) и требует отдельного ADR.
- Каталожная выдача строится от `ProductInfo` с `select_related` на
  `Product` (ADR-001), поэтому товары без активных предложений в
  выдачу не попадают и не требуют отдельной фильтрации.

## ADR-015 — Money representation

Date: 2026-08-29

Status: Accepted

Decision:

Денежные значения хранятся как `DecimalField(max_digits=12,
decimal_places=2)`.

- `catalog.ProductInfo.price`, `catalog.ProductInfo.price_rrc` —
  `DecimalField(12, 2)`.
- Snapshot-поля цены в `orders.OrderItem` (ADR-003) объявляются тем же
  типом.
- В коде денежные значения — только `decimal.Decimal`; `float`
  недопустим в вычислениях, сериализации и сравнениях.
- Значения из прайса поставщика (в `private/shop1.yaml` — целые числа)
  приводятся к `Decimal` на этапе валидации импорта.
- Валюта одна и в схеме не хранится.

Reason:

- Цены участвуют в финансовых расчётах (сумма заказа, накладная
  администратору). `PositiveIntegerField` из референсного кода
  требований делает невозможными копейки, а `FloatField` даёт ошибки
  округления при суммировании позиций.
- Тип должен быть выбран до первой миграции каталога: изменение типа
  колонки цены после появления заказов затрагивает и snapshot-поля
  `OrderItem`, то есть исторические финансовые данные.

Consequences:

- `max_digits=12, decimal_places=2` допускает значения до
  9 999 999 999.99 — с запасом для розничных цен.
- Суммы заказа вычисляются в `Decimal`; агрегация в БД
  (`Sum`, `F`-выражения) возвращает `Decimal` без потери точности.
- DRF по умолчанию сериализует `DecimalField` в строку
  (`"110000.00"`), что сохраняет точность на клиенте. Настройка
  `COERCE_DECIMAL_TO_STRING` на текущем этапе не меняется; формат
  ответа фиксируется в `docs/api.md` при реализации API каталога.
- Мультивалютность потребует отдельного поля и нового ADR; сейчас
  предполагается единая валюта прайсов.

## ADR-016 — Catalog service boundary

Date: 2026-08-29

Status: Accepted

Decision:

Граница между приложениями `suppliers` и `catalog` при импорте прайса
проходит по публичному сервисному слою `catalog.services`.
`catalog` может зависеть от `suppliers.models`
для своих собственных `FK` и внутренних операций.
`suppliers` не может зависеть от `catalog.models`.

Разделение ответственности:

- `suppliers` отвечает за источник и формат: получение файла (URL или
  локальный путь), `yaml.safe_load`, проверку структуры прайса,
  приведение типов (цены — к `Decimal`, значения характеристик — к
  строке), формирование объектов передачи данных.
- `catalog.services` отвечает за каталог: upsert `ProductInfo` по
  `(shop, external_id)`, `get_or_create` для `Category`, `Product`,
  `Parameter`, деактивацию отсутствующих предложений и границу
  транзакции (ADR-008).

Контракт:

- `catalog.services` принимает идентификатор магазина
  (`shop_id: int`) и провалидированные данные прайса в виде
  неизменяемых объектов передачи данных (frozen dataclass),
  объявленных в самом `catalog.services`. Приложение `suppliers`
  импортирует эти объекты из сервисного слоя — это разрешённое
  обращение к публичному интерфейсу, а не к ORM (ADR-002).
- Возвращается результат операции со счётчиками (создано, обновлено,
  деактивировано, реактивировано) — для логирования и последующего
  ответа API.
- Операция идемпотентна: повторный вызов с теми же данными не изменяет
  каталог.

Запрещено:

- импорт ORM-моделей `catalog` внутри `suppliers` (ADR-002);
- знание `catalog.services` о YAML, HTTP и Celery;
- обращение `catalog` к `suppliers.services` (обратная зависимость).

Reason:

- ADR-002 разрешает `suppliers` работать с данными каталога только
  через публичный сервисный слой; без явно зафиксированного контракта
  это правило нарушается первым же вызовом `ProductInfo.objects` из
  сервиса импорта.
- Разделение «формат против каталога» позволяет добавить другой формат
  прайса (CSV, JSON) или другой источник, не трогая логику записи, и
  тестировать upsert без файлов.

Consequences:

- Логика импорта разнесена по двум приложениям: разбор — в
  `suppliers/services`, запись — в `catalog/services`. Сквозной тест
  импорта покрывает обе части, upsert тестируется отдельно, без YAML.
- Транзакция открывается на стороне `catalog.services`: приложение
  `suppliers` не управляет границами транзакции каталога.
- Celery-задача `do_import` (ADR-005) остаётся в `suppliers` и вызывает
  тот же сервис, что и management-команда: асинхронность не меняет
  контракт.
- Валидация выполняется до открытия транзакции: прайс с ошибкой не
  оставляет частично обновлённых данных (ADR-008).

## ADR-017 — Import validation policy

Date: 2026-08-29

Status: Accepted

Decision:

Перед импортом прайса выполняется полная валидация входного файла.

Импорт запрещается если:

- goods отсутствует;
- goods пустой;
- дублируется external_id;
- неизвестная категория;
- цена < 0;
- количество < 0;
- превышены ограничения полей.


Reason:

Ошибочный файл не должен приводить к массовой деактивации каталога.

Consequences:

Каталог изменяется только после успешной валидации.

Amendment (2026-08-29, шаг 4.1)

Правила приведения значений характеристик товара.

- Булево значение YAML преобразуется: `true` → «да», `false` → «нет».
  Отклонять такие значения нельзя: они присутствуют в референсном прайсе
  требований (`private/shop1.yaml`, `"Smart TV": true`). Приведение
  через `str()` недопустимо — в карточке товара отобразилось бы «True».
- Составные типы YAML (список, отображение) в значении характеристики
  отклоняются: каталог хранит значение строкой
  (`catalog.ProductParameter.value`), и однозначного представления для
  них нет.
- Числовые значения приводятся к строке как есть (`6.5` → «6.5»).
- Преобразование выполняется парсером в приложении `suppliers` (ADR-016):
  `catalog.services` получает значения уже строками.
