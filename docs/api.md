# API

REST API на Django REST Framework.

Базовый префикс: `/api/`.

Формат обмена — JSON. Аутентификация — JWT (ADR-007), заголовок:

```
Authorization: Bearer <access>
```

По умолчанию все endpoints требуют аутентификации
(`DEFAULT_PERMISSION_CLASSES = IsAuthenticated`); публичные точки входа
помечены ниже явно.

Список выдаётся постранично (`PAGE_SIZE = 20`), ответ содержит
`count`, `next`, `previous`, `results`.


## OpenAPI

Схема генерируется drf-spectacular:

| URL | Назначение |
|---|---|
| `GET /api/schema/` | OpenAPI 3 схема (YAML) |
| `GET /api/schema/swagger-ui/` | Swagger UI |
| `GET /api/schema/redoc/` | ReDoc |

Проверка схемы (из каталога `backend/`):

```
uv run python manage.py spectacular --validate --fail-on-warn --file schema.yaml
```


## Реализовано

Приложения `users`, `catalog` и `orders` (базовая часть). Раздел
поставщика (`/api/suppliers/`) ещё не реализован — его правила описаны
в конце документа.

Разделы ниже описывают работающие endpoints. Правила, уже
зафиксированные ADR, но ещё не реализованные, вынесены в конец
документа — «Принятые решения по нереализованным разделам».


### Аутентификация и регистрация — `/api/auth/`

Все endpoints раздела публичные (`AllowAny`).

| Метод | URL | Назначение |
|---|---|---|
| POST | `/api/auth/register/` | регистрация пользователя |
| POST | `/api/auth/register/confirm/` | подтверждение email |
| POST | `/api/auth/login/` | получение пары JWT-токенов |
| POST | `/api/auth/token/refresh/` | обновление access-токена |
| POST | `/api/auth/password-reset/` | запрос восстановления пароля |
| POST | `/api/auth/password-reset/confirm/` | установка нового пароля |


#### POST /api/auth/register/

Запрос:

```json
{
  "email": "buyer@example.com",
  "password": "StrongPass123!",
  "first_name": "Иван",
  "last_name": "Иванов",
  "company": "ООО Ромашка",
  "position": "Менеджер",
  "type": "buyer"
}
```

Обязательные поля — `email` и `password`. Пароль проверяется валидаторами
Django (`AUTH_PASSWORD_VALIDATORS`) и не возвращается в ответе.

Ответ `201`:

```json
{"id": 1, "email": "buyer@example.com", "type": "buyer", "company": "", "position": ""}
```

Пользователь создаётся с `is_active=False` (ADR-004); письмо со ссылкой
подтверждения ставится в очередь Celery после коммита транзакции
(ADR-005, ADR-010). До подтверждения вход возвращает `401`.

Ошибки: `400` — email занят, email отсутствует, пароль не прошёл
валидацию.


#### POST /api/auth/register/confirm/

Запрос:

```json
{"uid": "MQ", "token": "de2zpa-d718bd48abf09570ea62040ca24fb648"}
```

`uid` и `token` приходят пользователю в письме (ссылка вида
`{FRONTEND_URL}/auth/confirm-email?uid=...&token=...`).

Ответ `200`: `{"detail": "Email подтверждён."}` — пользователь получает
`is_active=True`.

Ошибки: `400` — токен неверный, истёк, принадлежит другому пользователю
или уже использован. Токен одноразовый и живёт `PASSWORD_RESET_TIMEOUT`
секунд — в проекте 24 часа (ADR-011).


#### POST /api/auth/login/

Запрос: `{"email": "...", "password": "..."}`.

Ответ `200`: `{"access": "...", "refresh": "..."}`.
Время жизни: access — 60 минут, refresh — 1 сутки.

Ошибки: `401` — неверные данные либо неподтверждённый пользователь
(ответ намеренно не различает эти случаи).


#### POST /api/auth/token/refresh/

Запрос: `{"refresh": "..."}`. Ответ `200`: `{"access": "..."}`.

Rotation и blacklist не используются (ADR-007).


#### POST /api/auth/password-reset/

Запрос: `{"email": "..."}`.

Ответ `200` возвращается всегда, независимо от того, зарегистрирован ли
адрес: наличие пользователя в системе не раскрывается. Письмо отправляется
только активному пользователю и содержит ссылку вида
`{FRONTEND_URL}/auth/password-reset?uid=...&token=...`.


#### POST /api/auth/password-reset/confirm/

Запрос:

```json
{"uid": "MQ", "token": "...", "password": "AnotherStrong456!"}
```

Ответ `200`: `{"detail": "Пароль изменён."}`.

Ошибки: `400` — токен неверный/истёк/уже использован либо новый пароль не
прошёл валидацию. Токен одноразовый: после смены пароля он невалиден.
Срок жизни — общий для обоих типов токенов `PASSWORD_RESET_TIMEOUT`,
в проекте 24 часа (ADR-011).


### Профиль — `/api/users/profile/`

Требуется аутентификация.

| Метод | Назначение |
|---|---|
| GET | профиль текущего пользователя |
| PATCH | изменение `company` и `position` |

Ответ `200`:

```json
{"id": 1, "email": "buyer@example.com", "type": "buyer", "company": "ООО Ромашка", "position": "Менеджер"}
```

`email` и `type` доступны только для чтения. Переданные значения этих
полей игнорируются: смена email потребовала бы повторного подтверждения
адреса, смена `type` — изменения бизнес-роли пользователя.

PUT не поддерживается и возвращает `405`: полная замена профиля не имеет
смысла при двух изменяемых полях.

Ошибки: `401` — запрос без токена.


### Контакты — `/api/users/contacts/`

Требуется аутентификация. Пользователь работает только со своими
контактами: выборка ограничена `request.user`, обращение к чужому
объекту возвращает `404`.

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/users/contacts/` | список своих контактов |
| POST | `/api/users/contacts/` | создание контакта |
| GET | `/api/users/contacts/{id}/` | контакт по идентификатору |
| PUT / PATCH | `/api/users/contacts/{id}/` | изменение контакта |

Контакт описывает точку доставки: **кому** и **куда** (ADR-027).
Получатель не выводится из учётной записи — заказ оформляет один
сотрудник, а принимает товар другой.

Запрос на создание:

```json
{
  "last_name": "Петров",
  "first_name": "Пётр",
  "middle_name": "Петрович",
  "email": "recipient@example.com",
  "city": "Москва",
  "street": "Тверская",
  "house": "1",
  "structure": "",
  "building": "",
  "apartment": "",
  "phone": "+70000000000"
}
```

Обязательные поля: `last_name`, `first_name`, `city`, `street`, `phone`.
Необязательные: `middle_name`, `email` и остальные части адреса.
Владелец контакта берётся из токена и не передаётся в запросе.

`email` контакта — реквизит доставки, попадающий в накладную. Письма
сервиса (регистрация, сброс пароля, а в дальнейшем подтверждение заказа
и смена статуса) отправляются на `email` учётной записи и только на
него (ADR-027).

PATCH остаётся частичным: изменение одного лишь адреса не требует
передавать получателя. PUT задаёт контакт целиком, поэтому обязательные
поля нужны и в нём.

Контакты, созданные до появления этих полей, остаются читаемыми и
изменяемыми: поля получателя у них пусты, backfill намеренно не
выполнялся (ADR-027). Дополнить такой контакт можно запросом `PATCH`.

**DELETE не реализован** и возвращает `405`.

Исходная причина — адрес доставки участвует в истории заказов — снята
решением ADR-024: оформленный заказ хранит snapshot адреса, а
`Order.contact` объявлен `on_delete=SET_NULL`, поэтому удаление контакта
историю заказов не изменяет. `Contact` после этого — запись адресной
книги пользователя, а не историческая запись, и физическое удаление для
неё разрешено.

Endpoint появится вместе с приложением `orders`, в котором snapshot
адреса реализуется. До этого момента поведение API не меняется:
удаление контакта без snapshot оставило бы уже созданные заказы без
адреса.


### Каталог — `/api/catalog/`

Требуется аутентификация. Раздел доступен только на чтение: запись в
каталог выполняет импорт прайса (ADR-008, ADR-016).

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/catalog/products/` | список активных предложений |
| GET | `/api/catalog/products/{id}/` | предложение по идентификатору |

Выдача фильтрует только `ProductInfo.is_active=True` (ADR-025).
Приём заказов поставщиком и нулевой остаток на видимость **не влияют**:
отключение приёма заказов — временное состояние поставщика, а не снятие
товаров с продажи.

Элемент списка:

```json
{
  "id": 1,
  "product_name": "Смартфон Apple iPhone XS Max 512GB (золотистый)",
  "category": "Смартфоны",
  "model": "apple/iphone/xs-max",
  "shop": "Связной",
  "shop_accepts_orders": true,
  "price": "110000.00",
  "price_rrc": "116990.00",
  "quantity": 14,
  "parameters": [{"name": "Цвет", "value": "золотистый"}]
}
```

`shop_accepts_orders` и `quantity` присутствуют намеренно: без них
клиент узнавал бы о невозможности заказа только по ошибке при
добавлении в корзину (ADR-025).

Деактивированное предложение недоступно и по прямой ссылке: `404`.


### Корзина — `/api/orders/cart/`

Требуется аутентификация. Корзина — это заказ в состоянии `basket`
(ADR-009); отдельного ресурса корзины нет, `GET` создаёт её при первом
обращении.

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/orders/cart/` | корзина текущего пользователя |
| POST | `/api/orders/cart/items/` | добавление товара |
| PATCH | `/api/orders/cart/items/{id}/` | изменение количества |
| DELETE | `/api/orders/cart/items/{id}/` | удаление позиции |

Цена, наименование и остаток в корзине берутся из **текущего каталога**,
а не из snapshot: до подтверждения заказа snapshot не заполнен (ADR-003,
ADR-009). Сумма корзины пересчитывается при каждом запросе.

Запрос добавления: `{"product_info": 1, "quantity": 2}`. Повторное
добавление того же предложения увеличивает количество существующей
позиции, а не создаёт вторую строку.

`DELETE` — единственный метод удаления во всём API заказов (ADR-022).
Удаление последней позиции не удаляет корзину: `GET` вернёт пустую
корзину, а не `404`.

Ошибки:

| Код | Причина |
|---|---|
| `400` | `quantity` меньше единицы, неизвестный `product_info` |
| `404` | позиция не найдена в корзине текущего пользователя |
| `409` | товар недоступен для заказа |

Ответ `409` содержит машиночитаемый код причины — они различимы по
смыслу и требуют разных действий покупателя (ADR-025):

```json
{
  "detail": "Доступно 14 шт., запрошено 20 шт.",
  "code": "insufficient_stock",
  "product_info": 1
}
```

Коды: `offer_inactive` (снято с продажи — окончательно),
`shop_not_accepting_orders` и `insufficient_stock` (временно),
`offer_gone` (предложение удалено из каталога).

Обращение к чужой позиции возвращает `404`, а не `403`: существование
чужих данных не раскрывается.


### Оформление заказа — `/api/orders/checkout/`

| Метод | URL | Назначение |
|---|---|---|
| POST | `/api/orders/checkout/` | подтверждение заказа |

Запрос: `{"contact": 1}`. Выполняется переход `basket` → `new`
(ADR-022): в одной транзакции фиксируются получатель и адрес (ADR-024,
ADR-027), наименование, магазин и цены каждой позиции (ADR-003), и
проставляется `confirmed_at`.

Остатки **не списываются и не резервируются**: полем `quantity` владеет
прайс поставщика, и ближайший импорт перезаписал бы списание (ADR-022,
ADR-008).

Ответ `201` — карточка заказа (см. ниже).

После коммита оформления ставятся два письма (ADR-005): покупателю — на
email учётной записи, администратору — накладная на `ORDER_ADMIN_EMAIL`.
Отправка асинхронна и на ответ не влияет: недоступность почты не делает
заказ неоформленным.

Ошибки:

| Код | Причина |
|---|---|
| `400` | пустая корзина; контакт не существует или чужой; в контакте не заполнены данные получателя |
| `409` | позиция стала недоступна между добавлением и оформлением |

Неполный контакт возвращает перечень недостающих полей — покупателю
нужно знать, что дописать (ADR-027):

```json
{"contact": ["Не заполнены обязательные поля получателя: last_name, first_name"],
 "fields": ["last_name", "first_name"]}
```


### Заказы — `/api/orders/`

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/orders/` | история заказов |
| GET | `/api/orders/{id}/` | заказ по идентификатору |

Выборка ограничена собственными заказами; корзина в историю не попадает
(ADR-009). Обращение к чужому заказу возвращает `404`. `DELETE` не
предусмотрен — маршрута нет: заказ является исторической записью
(ADR-022).

Элемент списка — «Номер, Дата, Сумма, Статус» (`private/screens.md`):

```json
{"id": 1, "confirmed_at": "2026-08-30T15:00:00Z", "state": "new", "total": "220000.00"}
```

Состояния: `new`, `confirmed`, `assembled`, `sent`, `delivered`,
`canceled` (ADR-022). Смену статуса после `new` выполняет администратор
в Django Admin; через API она недоступна ни покупателю, ни поставщику.

Карточка заказа дополнительно содержит `items` и `delivery`. Обе части
читаются из snapshot самого заказа, а не из каталога, связанного
`Contact` или учётной записи: предложение могло измениться, контакт —
быть удалён, а заказ мог быть оформлен на другого получателя (ADR-003,
ADR-024, ADR-027). Сумма заказа считается по зафиксированным ценам,
поэтому импорт прайса её не меняет.


### Поставщик — `/api/suppliers/`

Раздел доступен пользователям с `type='shop'`; покупатель получает
`403`, аноним — `401`. Поставщик работает через API и доступа в админку
не получает (ADR-023).

| Метод | URL | Назначение |
|---|---|---|
| POST | `/api/suppliers/` | создание своего магазина |
| GET | `/api/suppliers/{id}/` | свой магазин |
| POST | `/api/suppliers/{id}/import/` | запуск импорта прайса |
| GET | `/api/suppliers/{id}/imports/` | журнал запусков |

Запрос создания: `{"name": "Связной", "url": "https://.../price.yaml"}`.
Владелец берётся из токена и в запросе не передаётся (ADR-012). На
пользователя приходится один магазин: повторный `POST` возвращает `400`.
Приём заказов (`state`) доступен только для чтения — это отдельное
действие поставщика, а не поле формы. Магазин **не создаётся** как
побочный эффект импорта.

Запуск импорта тела запроса не имеет: источник — ссылка магазина.
Ответ `202`:

```json
{"import_id": 12, "status": "queued"}
```

Ответ не означает успешного импорта — он означает, что запуск
зарегистрирован. Результат читается из журнала (ADR-021). Проверки
адреса (только `https`, таймауты, лимит размера, защита от SSRF)
выполняет загрузчик, а не API: их вердикт попадает в
`ImportLog.error_code` (ADR-018). Следствие: адрес с `http://` получает
`202` и завершается отказом `insecure_source` в журнале, а не
немедленным `400`.

Ошибки запуска:

| Код | Причина |
|---|---|
| `400` | у магазина не указана ссылка на прайс |
| `404` | чужой или несуществующий магазин |
| `409` | импорт этого магазина уже выполняется (`code: import_already_running`) |

Журнал возвращает записи только своего магазина: состояние, число
попыток, счётчики результата, код и текст ошибки. `DELETE` не
предусмотрен ни для магазина, ни для журнала — исторические записи не
удаляются (ADR-012, ADR-021).

Не реализовано и остаётся принятым (ADR-026, amendment): переключение
приёма заказов и список заказов поставщика.
